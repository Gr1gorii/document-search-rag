# Проверка качества document-search-rag

Проверены поиск, локальный RAG и интерфейс. Приложение работает, но ответы маленькой модели требуют сверки с исходным текстом: валидная ссылка не гарантирует фактическую правильность.

## Условия

Apple M3, 16 ГБ RAM, macOS, Python 3.10, уже установленная `qwen3:1.7b` через локальную Ollama. Корпус: 12 сохранённых страниц FastAPI, 135 фрагментов. BM25 → top 4 → score ≥ 2.0 и query coverage ≥ 0.6 → генерация. Температура 0, seed 42, контекст 8192, максимум 480 токенов. Настройки не означают побитовую воспроизводимость разных версий backend.

Время реальных запусков и SHA-256 корпуса/набора записаны в JSON. В JSONL есть вопрос, найденные фрагменты, окончательный ответ, ссылки, причина отказа и черновик модели, если она вызывалась. Время отказа до генерации нельзя сравнивать со временем сгенерированного ответа как скорость модели.

## Набор разработки: 60 вопросов

45 вопросов о корпусе и 15 вне него. Это черновая разметка `draft_unreviewed`, не независимый benchmark. После первого прогона на этом наборе добавлена проверка покрытия вопроса. Одновременно исправлена обработка лишних объявленных citation IDs; изменения не являются изолированным экспериментом только с одним фактором.

Поиск сам по себе не генерирует ответ. Его gate отклонил 13/15 вопросов вне корпуса; модель отказала на оставшихся двух. Результаты поиска в интерфейсе показываются без этого gate: пользователь может самостоятельно посмотреть даже частичные совпадения.

До coverage guard модель отвечала на 8/15 вопросов вне корпуса, включая выдуманные Kubernetes, JWT, WebSocket и Redis рекомендации. Этот прогон сохранён в `before-coverage-guard.*`, а не скрыт. Отдельный `initial-integration-failure.*` содержит более ранний технический провал несовместимой JSON-схемы; он не является оценкой фактического качества модели.

## Выборочная сверка с текстом

В `source-spot-checks.json` записана сверка 14 выбранных примеров ассистентом. Это целевой просмотр удачных и проблемных случаев, не случайная выборка и не ручная проверка всех 72 вопросов независимым рецензентом. Исходная разметка остаётся `draft_unreviewed`.

Особенно важны два провала:

- **q10**: модель добавила выдуманное условие о префиксе `item:`. Источник объясняет распознавание по типу Pydantic-модели. Наличие слова `Pydantic` позволяет ошибочному ответу пройти keyword proxy.
- **q28**: модель написала, что background tasks выполняются **до** отправки ответа. Цитируемый `background-tasks-000` говорит **после** возврата ответа. Keyword proxy тоже прошёл: слова `after` и `response` оказались в другой части текста.

Дополнительные случаи: q16 не объясняет сохранение явно заданных значений, равных default; p02 добавляет утверждение, отсутствующее в конкретном фрагменте; p03 ссылается на создание функции, а не на момент её выполнения. Напротив, q21 о `raise HTTPException`, q26 об OpenAPI, q45 о `read/seek` и p06 об origin подтверждаются выбранными фрагментами.

Поэтому **91.11% - проверка слов, а не точность ответов**. 100% валидных citation IDs и совпадений со страницей также не являются 100% поддержкой утверждений.

## Методика

`gold_page_hit_at_k`: хотя бы один из первых k фрагментов относится к ожидаемой странице. `MRR@4`: среднее обратного ранга первого такого фрагмента; отсутствие даёт 0. Это метрики страницы, не точного подтверждающего отрывка.

Keyword proxy требует хотя бы одну подстроку из каждой группы `expected_terms`, без учёта регистра. Отказ и ошибка на ответимом вопросе дают 0. Поиск проверяется на объединении четырёх фрагментов. Подстроки и отсутствие проверки логики делают метрику слабой; q28 показывает конкретный ложноположительный результат.

`citation_page_precision`: доля выданных ссылок на gold page. Отказов в знаменателе нет. `citation_id_validity`: доля выданных ответов, чьи ссылки принадлежат найденным фрагментам; валидность дополнительно обеспечивается кодом. Эти метрики не проверяют содержание предложения.

`abstention_recall`: доля неответимых вопросов со статусом `abstained`. `false_abstention_on_answerable`: доля ответимых со статусом `abstained`. Технические ошибки считаются отдельно и не засчитываются как отказ.

p50 - медиана; p95 - наблюдение с рангом `ceil(0.95 × n)`. После уточнения определения p95 сводки пересчитаны из сохранённых времён, без повторной генерации или изменения ответов. Это один последовательный запуск, а не нагрузочный тест; малая новая выборка даёт неустойчивые оценки.

## Проверки приложения

- Ruff lint, форматирование, strict mypy.
- 23 теста без модели: поиск, ссылки, отказ до генерации, модельный отказ, сбой/таймаут, ввод, API, контрольные суммы, якоря и идентичная пересборка корпуса.
- Один live-тест: реальный ответ на вопрос про HTTPException 404 и отказ на вопрос о столице Франции.
- Headless Chrome с временным профилем: домашняя страница, кнопка примера, поиск, реальный RAG, раскрытие источника, отказ, ширина 390 px без горизонтального переполнения. HTTP 503 в UI намеренно имитируется; остальные запросы реальные. Ошибок JavaScript нет. Подробности в `ui-checks.json`, скриншоты в `ui-*.png`; desktop и mobile просмотрены визуально.

В проверенной версии Starlette есть предупреждение о будущей замене httpx в TestClient. Тесты проходят с зафиксированными зависимостями; это не скрытая ошибка и не основание считать другие версии проверенными.

## Что остаётся

Для уверенного справочника нужен отдельный обзор фактической поддержки предложений и более сильная работа с перефразированием. Следующий осмысленный эксперимент - сравнить retrieval и generation отдельно на новой разметке, а не снижать guard до красивой цифры на тех же вопросах. Новые модели для этого MVP не скачивались.

Регистрация проекта в Codex остаётся технически недоступной из этой делегированной среды: инструмента добавления папки и UI runtime нет. Папку можно добавить вручную, затем переместить зарегистрированный проект в существующий раздел «Работа и портфолио» поддерживаемым инструментом. Внутренние базы приложения, существующие проекты и их порядок не изменялись.
